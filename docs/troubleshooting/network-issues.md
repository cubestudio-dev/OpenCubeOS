# Network troubleshooting

Ordered triage first, then the four deep chains: DHCP, DNS, TLS
self-signed refusal, and the per-NIC `init failed` template.

## Ordered triage

Run `net-tool` and walk the menu, or use the classic spellings:

```
ush> lspci                  (is the NIC on the bus?)
ush> ip                     (address bound? 0.0.0.0 = none)
ush> dhcp                   (address + gateway + DNS in one shot)
ush> ping 10.0.2.2          (ICMP to the QEMU gateway)
ush> arp                    (L2 resolution happened?)
ush> dns example.com        (UDP + resolver OK?)
ush> wget example.com 80 /  (full TCP + HTTP round trip)
ush> tcpstats               (per-connection counters)
```

Each step isolates a layer: bus → driver → L2 → L3 → L4 →
application. The `update` wizard runs the first steps of exactly this
ladder (IP probe → DHCP offer → DNS) before it ever checks for
updates. `netstat` and `ifconfig` give the socket/interface pictures.

## The DHCP failure chain

DHCP is a 4-step exchange — DISCOVER → OFFER → REQUEST → ACK on ports
68/67, magic cookie 0x63825363, xid 0x12345678; options parsed: 53
(msg type), 54 (server id, echoed in REQUEST), 1 (mask), 3 (gateway),
6 (DNS). The single failure string is `DHCP failed (timeout)` — the
chain broke somewhere and the timeout swallowed the detail. Walk it:

1. **Is there a NIC at all?** `lspci`; the driver's status command
   (`e1000`, `rtl8139`, ...). `ip` shows the bound driver name.
2. **Did the driver bind?** The `<nic>: init failed` template below.
3. **Is L2 alive?** `arp` — after any traffic attempt there should be
   the gateway's MAC. Nothing there = no frames flow.
4. **Is the server answering?** QEMU user-mode networking always
   answers (10.0.2.2 gateway + DNS forwarding, no host configuration
   needed). Real LAN: check the DHCP server's logs.
5. **Re-run** `dhcp` — a success prints the anchor `DHCP success: IP=...` plus mask/gateway/DNS. Exit code reflects the outcome.

If DHCP succeeds but the DNS field is empty, set it via a static `ip`
or re-run DHCP (option 6 parsing is part of the chain).

## The DNS failure chain

`dns <name>` (optionally `dns <name> aaaa|cname|mx|txt|ns|srv`).
Failure strings: `DNS resolution failed`, `DNS resolution failed (timeout)`, `timeout`, and the per-record honest tails (`MX: no mail exchanger (or timeout)`, `AAAA: no IPv6 record (or timeout)`,
`CNAME: not a CNAME or resolution failed`, ...).

1. **Is there a DNS server configured?** It comes from DHCP option 6
   or a static `ip` round — `ifconfig` prints the DNS field.
2. **Is UDP flowing?** `ping <dns-server-ip>`; `arp` for the gateway.
3. **Does the resolver work at all?** `dnstest` (the battery, incl.
   built-in vectors against 10.0.2.2 and the update.json fixture).
4. **Poisoning guards** (klog): `wrong transaction id dropped`,
   `query (QR=0) dropped`, `wrong qname echo dropped` — responses that
   fail validation are dropped silently. On a hostile LAN, known
   boundary: the transaction ID and response validation hardening is
   BUG-22 class.
5. Counters `UDP rx dropped (buffer full)` / `IP frag dropped` in
   netstat-family output mean overload, not misconfiguration.

## TLS and the self-signed refusal (HTTPS E2E item 0)

The trust model: certificate chains must anchor in the embedded root
store (ISRG Root X1 etc., DER generated by `tools/embed_roots.py`).
Verification failures print the exact stage and then refuse:

```
[tls] x509 verify failed: <why> - connection REFUSED
```

where `<why>` is one of `bad certificate format`, `unsupported algorithm`, `signature verification failed`, `hostname mismatch`,
`issuer certificate missing` (the X509_E_* family —
[error-codes.md](error-codes.md)).

**HTTPS E2E item 0 semantics**: the *zeroth* check of the HTTPS E2E
suite is that a **self-signed chain is REFUSED by default**. This is
the acceptance test for BUG-21 (the old code only warned and
continued — a MITM needed just a self-signed cert). So:

- Seeing the REFUSED line with a self-signed server is **correct
  behavior**, not an outage.
- Testing against a self-signed reference server requires the explicit
  opt-in: `config set tls.insecure 1` (the E2E compatibility pass uses
  exactly this), and turning it back off afterwards.
- Handshake step failures beyond verification (`ServerHello recv/parse failed`, `ServerHello legacy version mismatch`,
  `CertificateVerify recv failed`, `server Finished verify_data mismatch`, `record decrypt failed (AEAD open)`) name the broken step
  directly — read the message; TLS 1.2 with DHE-RSA-AES128-SHA256
  (0x0067) is the reference negotiation.
- `wget https://host/path` is the client face (`https://` selects TLS,
  port 443 default).

## The per-NIC `init failed` template

Every ethernet driver prints the same failure shape when its probe
fails: `<name>: init failed` — `e1000e`, `igb`, `ixgbe`, `rtl8139`,
`rtl8168` (rtl8169 face), `bcm57xx` (plus its special
`bcm57xx: DMA memory above 4GiB - refused`). One unified triage:

```
ush> lspci                       # 1. is the card on the bus at all?
ush> pcidump 0:03.0              # 2. are the BARs sane? (use the real b:d.f)
ush> e1000e                      # 3. the family status command
ush> e1000e_test                 # 4. the family selftest
ush> nic_rw_test                 # 5. generic NIC loopback
ush> other_nic_test              # 6. best-effort families (3c59x/nForce/AR81xx/Marvell)
```

- No PCI device → wrong QEMU flag or the card is not seated; QEMU's
  best-tested path is `-device e1000` on a user netdev.
- Device present but `init failed` → BAR/DMA problems
  (`pcibars`, `pcie`); on bcm57xx specifically, DMA above 4 GiB is
  refused.
- Status OK but no traffic → link/routing: `ifconfig` (link state),
  `route`, `arp`.
- `virtio TX timeout: avail_idx=... used_idx=...` — the virtio NIC
  stopped consuming descriptors; restart the VM/device, report if
  persistent.

Wireless: `wifi` (status), `wifi scan` (passive scan — QEMU honestly
reports no radio), `wifi test` (core + per-family selftest),
`wifi sdio`. Security strings `WEP/WPA1/WPA2 (not supported)` are the
honest state machine, not failures.

## SSH / sshd specifics

- Client defaults: port 2222, user `oc`, password `oc`; password `-` =
  publickey with `/etc/ssh_client_key` (falls back to password if the
  key is absent). Hostnames are DNS-resolved.
- Host trust is TOFU: the first connection writes
  `/etc/ssh_known_hosts`; a changed key prints `[ssh] WARNING: HOST KEY CHANGED! (possible MITM)` and refuses — delete the entry only
  when you know why it changed. On a read-only /etc expect
  `[ssh] TOFU: cannot write /etc/ssh_known_hosts`.
- Server: `sshd [port]` (default 22), one session at a time; second
  connections are refused (`too many connections (one session at a time)`). First boot generates the host key in the background
  (`host key file corrupt; regenerating`); if it cannot
  (`cannot obtain a per-installation host key - refusing to start sshd`), pre-seed `etc.img` with `tools/host_keygen_etc.py`.
- **First connect stalls**: the ARP cache is cold after DHCP — run one
  client-direction command first (`ping` the peer) to warm it.
- TCG (no-KVM) QEMU is slow: RSA-2048 keygen can exceed 500 s — the
  E2E recipes pre-seed keys and use generous timeouts (banner 420 s).

## QEMU specifics

- User-mode networking always provides 10.0.2.2 (gateway) and DNS
  forwarding — no host configuration needed.
- The default `-device e1000` is the best-tested path.
- Two-instance tests: shared `-netdev socket,multicast=...` gives a
  real two-node link for the NIC tests.
- Timing stability for network tests: QEMU's `-icount`.

## Firewall and routing

The full netfilter face (`firewall` lists rules; `add`/`del`/
`policy`/`ct`/`reset` manage them):

```
ush> firewall                                    # list rules + policies
ush> firewall add in drop tcp port 22            # drop inbound SSH
ush> firewall del 1                              # remove rule 1
ush> firewall policy in accept                   # chain default
ush> firewall ct                                 # conntrack table
ush> firewall reset                              # rules + conntrack + policies
```

- `rule not found` — the `del <n>` index was stale; re-list first.
- Ping stops working after experiments — check the input-drop rules
  and `firewall reset` (it also clears conntrack and policies — that
  is the point).
- `nf_test` is the self-verifying battery (input drop + hits, rule
  removal restores ping).

Routing: `route` shows the default + up to 16 custom entries;
`route add <dst> <mask> <gw>` / `route del <dst> <mask>`. A
`connect failed` with a present gateway usually means the peer, not
the table — but an ARP entry that expired mid-session can dead-wait
(known BUG-24 class under retransmit pressure): re-`ping` the peer to
re-resolve.

## Counters that tell the story

- `netstat` — sockets and connection statistics.
- `tcpstats` — per-connection state, cwnd/ssthresh/mss/rto,
  retransmit queue length, dup ACKs, timestamps, cc=cubic, w_max,
  sack, srtt/rttvar. RTO climbing + dup_acks growing = loss on the
  path.
- `  UDP rx dropped (buffer full): <n>` / `  IP frag dropped: <n>`
  (statistics output) — overload counters, not configuration errors.
- `arp` — the 16-entry cache; the gateway's MAC should appear after
  any traffic. An empty cache with a bound IP means L2 is dead
  (driver/link).
- `ifconfig` — read-only: driver name, HWaddr, inet, mask, gateway,
  DNS, link state, RX/TX counters. `ip` shows the same address block;
  `ip <a> <m> <g>` is the static-set form (the wizard's static-IP
  path asks the three fields in exactly this order).

## Two-node and host-access setups

- Host reaches guest `sshd`: `-netdev user,id=n1,hostfwd=tcp::2223-:22`
  then `sshd 22` in the guest; connect from the host to
  `localhost:2223`.
- Real two-node link: shared `-netdev socket,multicast=...` on both
  instances (the NIC tests use it).
- The BT stack is real E2E over COM2 H4 bytes (`bt test` against the
  `bt_test_peer.py` host peer).
