# 3.0.0-WP-tui-input-encoding-hardening — TUI input and encoding hardening
The input/encoding/display hardening batch: five user-reported
defects driven to root cause with reproduction evidence on every one,
plus the full three-chain sweep behind them.  Every fix follows the
"standard discipline, no per-platform special-casing" rule.

## Changes

### 1. TUI entry hiding (registered, unlisted)
The eight legacy TUI sub-launchers (`tui-test`, `tui-hw`, `tui-net`,
`tui-sysinfo`, `tui-time`, `tui-drv`, `tui-sys`, `tui-ext`) stay
registered and directly executable - only their LISTING is gone:
`help` and `help -a` no longer show them, the desktop tree lost the
Extensions lab mirror node, and the reconciled calibers are 311
registered / 292 listed / 8 hidden (the presentation gates assert
both numbers).  No code path was removed; the single fact source is
the `k_hidden[]` table in `l1_tui_entry_filter.c`.

### 2. The OCIRE space capture (root cause: a scan-code bounds overrun)
`lang zh` typed as `LANGZH`, every spaced command broken: the PS/2
scan-code decoder indexed a table one entry past its end - the
space bar's make code (0x39) fell off and read adjacent memory as
the ASCII mapping.  Fixed at the table; the six-path matrix (OCIRE
and OCOS x serial, PS/2, UEFI) is all green, `LANG ZH`, `LANG EN`
and every spaced command included.

### 3. The cross-write UTF-8 TTY
The ush line editor echoed each key event as a one-byte write; a
pasted or IME-committed CJK glyph arrives as 3-4 such writes and the
console decoded each independently - a lone lead byte painted as a
raw Latin-1 cell, every hanzi echoed as solid blocks until a
full-line redraw happened to fix it.  The TTY now reassembles
multi-byte sequences across writes (`core_tty_utf8.c`): receive and
echo are byte-exact, `cat` of a UTF-8 file returns the exact
sequence, backspace deletes a WHOLE character (the 2-cell wipe on
the wire), the 80-cell wrap never splits a glyph, and advance is
per-CHARACTER.  VLM-read VGA screendumps + raw-byte hexdumps in the
evidence.  Not in scope (unchanged by design): input methods, a
locale system, filename normalization.

### 4. Serial encoding direction (verdict, no code change)
Raw-byte captures of both serial paths: the kernel output is
uniformly valid UTF-8, OCBL emits pure ASCII + standard ANSI CSI
(the same sequences GRUB's serial menu emits), and the built-in
`serial_encoding=gbk` tee converts correctly in both directions.
The reported "COM1 garbled output" is the host terminal decoding -
the reporter's Windows host runs codepage windows-936 (GBK) reading
a UTF-8 stream.  Registered, not a code defect.

### 5. The VMware triple-fault fix (five findings, four code fixes)
The delivered `vmware.log` (15 `Triple fault.` events, ~1.24 s per
cycle) and boot serial were driven to a full reasoning chain (the
verbatim quotes, the crash-phase mapping and the hypothesis matrix
are in `evidence/.../vmware/vmware-reasoning.md`):

- **H1 - the OCBL core never loaded an IDT.**  The 64-bit core
  inherited the firmware's real-mode IVT state (`{0, 0x3FF}`),
  which misdecodes any vectoring in long mode - an asynchronous
  event escalated #GP -> #DF -> triple fault.  OCBL now builds its
  own 256-gate table (`ocbl_idt.c/.S/.h`): exceptions report on
  serial and halt, IRQs/NMIs iretq; the real-mode trampoline swaps
  the vectoring discipline at every mode boundary (the firmware IVT
  going down, our table coming back up).  Proven deterministically
  without VMware: an NMI latched at a breakpoint in pure 64-bit
  OCBL code kills the pre-fix build (the reset path) and is
  absorbed by the fixed one.
- **H2 - the El Torito boot drive number is firmware-chosen** (the
  reporter's VMware passes 0x9F, not 0xE0+): the scan never saw the
  boot CD, the menu fell back to the Shutdown countdown.  Gated on
  the El Torito flavor now.
- **H3 - the state monitor's EBDA guard read I/O ports instead of
  the BDA memory word**, so it never fired and the state pages could
  land in BIOS-private low memory (the "next INT call
  triple-faults" class).  Forced-build proof: the guard fires, the
  kernel honors `oc.stmon=off`, the boot completes.
- **H4 - the page-table relocation for low-EBDA machines targeted
  the trampoline's own address** and the return path hardcoded
  CR3.  Relocation target moved with a single-source-of-truth
  publish; forced-build matrix: the new target boots, the old one
  dies on both pre-fix and post-fix builds.
- Plus: CMOS register selects keep the NMI mask set, and the UEFI
  getkey accepts the CSI-arrow tails OVMF's ConIn can steal.

### 6. The extended sweep
Re-audit of the input/encoding/display chains on the final tree.
The BIOS menu's serial keying was dead (the int 14h route never
delivers under SeaBIOS) - now reading the 16550 directly, verified
live.  A regression of this very batch (installing our IDT under
UEFI kills OVMF's interrupt-driven drivers) was caught and fixed
before shipping - the IDT install is BIOS-flavor only.  The OVMF
menu input starvation is registered as K-06 with workarounds.

## Known issues

- **K-06 - the OCBL menu cannot be driven from the keyboard under
  OVMF while boot services are live.**  No input source delivers
  (serial bytes are drained by OVMF's terminal driver and never
  resurface through ConIn; PS/2 equally starved) - the menu
  auto-boots the default entry after the 10 s countdown.  The BIOS
  flavor's menu is fully keyable (serial + PS/2).  Candidate future
  fix: a WaitForEvent-based menu loop.
- K-01/K-02/K-03/K-05 carry over unchanged (see KNOWN_ISSUES).
