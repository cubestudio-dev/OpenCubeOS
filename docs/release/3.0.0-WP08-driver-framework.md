# 3.0.0-WP08-driver-framework — the driver framework

The L0 driver-framework batch: the six capabilities that turn "add a
driver by adding a file" from a naming convention into an enforced
engineering standard - metadata, a device tree, power hooks, hotplug
events, failure isolation and a deterministic init order.  The legacy
`OC_DRIVER_DECL` path is untouched and coexists (existing drivers
needed zero changes; both registration paths are collected at boot).

## Changes

- **Driver metadata and dependencies.**  A new descriptor -
  `oc_driver_info_t` (name, version, author, license, dependency
  list, compatible device types, priority hint, D-state mask, and
  init/probe/remove/suspend/resume callbacks) - registers through
  `OC_DRIVER_INFO_DECL` into the new `.oc_drvi` linker section.  The
  old macro keeps its exact signature and behavior.
- **A device tree without ACPI.**  Node model (id, parent, children,
  type, MMIO/IOPORT/IRQ/DMA resources, binding state, private data),
  register/unregister, lookup by id or name, by-type / by-child /
  depth-first iteration.  The framework parses no ACPI and enumerates
  no bus - WP-09a/WP-09b will fill the tree through the same
  register calls.
- **Driver-level power hooks.**  `oc_pm_notify(D1..D3)` suspends
  children-first, `oc_pm_notify(D0)` resumes in reverse; drivers
  that never declared the target state are skipped.  No S-state
  machine, no policy - WP-22 calls the interface.
- **A generic hotplug event queue.**  IRQ-safe `oc_hotplug_post()`,
  process-context `oc_hotplug_drain()`, filtered subscriptions by
  device type or node id, drop-and-count overflow accounting.  The
  concrete bus triggers stay with WP-09a/WP-14a.
- **Failure isolation.**  A probe or init failure is recorded
  (driver, error code, count, timestamp), the node stays visible as
  unbound-with-error, and the boot carries on - never a panic, never
  a blocked walk.  `drv reload` retries; the ledger clears only on a
  clean comeback.
- **A deterministic init order.**  Topological over the declared
  dependencies (Kahn's algorithm, priority-hint + name tie-break) -
  byte-identical across reboots and rebuilds, never link order.
  Cycles and missing dependencies are isolated with a report instead
  of a silent loop.
- **Application dictionary.**  Full re-capture on this image: 308
  commands (284 + the 16 new), every entry a real executed
  transcript in both languages (the verify gate passes
  308 = registry = enumeration = EN = zh).

## New interfaces

- `OC_DRIVER_INFO_DECL` (ocos/drivers/framework/interface/core_drv_meta.h)
  - the metadata registration macro (.oc_drvi section)
- `oc_devtree_register/unregister/find/find_name/add_res` and the
  by-type / by-child / DFS walkers (core_devtree.h) - the device tree
- `oc_pm_notify` / `oc_pm_nodes_in_dstate` (core_pm_hook.h) - the
  driver power-state change request (for WP-22)
- `oc_hotplug_post / drain / subscribe / unsubscribe` and the
  per-owner delivery stats (core_hotplug.h) - the event surface (for
  WP-09a/WP-14a)
- `oc_drv_fail_note/count/at/clear` (core_drv_isolation.h) - the
  failure query interface
- `oc_drvfw_boot/bind/unbind/reload/detach_subtree/bind_pass`
  (core_drv_registry.h) - the registry operations
- `svc_diag_drvfw_dispatch` (services/diag/interface/svc_diag_drvfw.h)
  - the shared diag-surface implementation
- `l1_diag_drv_cmd/dev_cmd/drv_sub/dev_sub`
  (ocos/interface/l1_diag_cmds.h) - the shared ring-3 command layer

## New shell commands

- `drv` - driver framework diagnostics (umbrella; subcommands list,
  info, failed, bind, unbind, reload, debug, order, help)
- `dev` - device tree diagnostics (umbrella; subcommands tree, list,
  info, debug, help)
- `drv_list` `drv_info` `drv_failed` `drv_bind` `drv_unbind`
  `drv_reload` `drv_debug` `drv_order` `drv_help` - the standalone
  twins of the drv subcommands (byte-identical output)
- `dev_tree` `dev_list` `dev_info` `dev_debug` `dev_help` - the
  standalone twins of the dev subcommands

## Known issues

- **K-04 - `pmmrace` can panic the kernel (pre-existing).**  The
  PMM race detector's own race (non-atomic bitmap vs the IRQ-context
  allocator) can corrupt live frames; reproduced on the previous
  release baseline (f5af2ab).  This batch's boot work shifts the
  IRQ/loop phase and makes the fatal interleaving likelier.  The fix
  is PMM IRQ-atomicity - a separate work package.  Until then a
  `pmmrace` PASS verdict only covers the rounds it survived.
- **K-05 - a fresh clone can rotate the OCIRE key.**  `ocire.mk`
  regenerates the Ed25519 public key whenever the generator script's
  mtime beats the committed file's; the rotated key is committed
  with this release so git matches the artifacts.

Evidence: `evidence/wp08-driver-framework/` (boot logs, gate and
test outputs, the K-04 reproduction transcripts).
