## ① VMware 启动龟速根因（B-vmx1）

- **根因不是期限而是负载**：VMware 下每一次 inb/MMIO 读都是一次 VM exit
  （1–3 µs），而热轮询循环每迭代一次读一个端口且无空闲节拍；另有一个
  以 4096 **迭代次数**（QEMU 上几微秒、VMware 上 10+ ms 的 exit 时间）判定
  "命令丢弃"的启发式——每个启动偏慢的健康虚拟盘都会被判死、中止、
  20000 次 io_wait 空转、再在 1000 ms 期限内重试至多 8 次：分钟级启动。
- **修复**：`driver_tsc_pause_us()`（零端口 I/O 的 TSC 微秒自旋）为全部热
  轮询配速（BMDMA 25 µs、ATA status/AC97 codec/HDA stream/e1000 EEPROM
  每 50 µs 一读）；丢弃判定改为**真实时间门**（10 ms 墙钟 BMIS==0 且
  task file 空闲——QEMU 上真丢弃仍会空满期限、健康传输永不空这么久）；
  20000 次 io_wait 空转改 2 ms TSC 停顿；OCBL 菜单循环（两味）在
  int16h/LSR/CMOS 轮询之间纯 CPU 停顿；早期控制台 COM1 THRE 等待有界。
- **新证据面**：内核在每次 L1_READY 时打印
  `[perf] ata_dma: port_io=... polls=... xfers=... retries=... drops=... wait_ms=...`。
  QEMU TCG 实测（16 MiB FAT32 /etc 盘、45 次 DMA 传输、修复前后计数对比）：
  port_io **17,608,313 → 39,452（446 倍）**，菜单迭代 **130,589 → 117
  （1116 倍）**。VMware 上每个计数操作即一次 VM exit：修复前 18–53 秒纯
  exit 处理 + 假丢弃重试风暴（分钟级），修复后 0.04–0.12 秒。
- 证据：`evidence/wp-severe-fix-and-closure/b-vmx1-vmware-performance.md`。

## ② K-08：ush 横幅 uname 偶发竞态（按构造关闭）

- **根因（monitor hunter + 2.7 GB 中断 trace 实况捕获）**：
  `l1_launcher_boot_default()` 在 `user_process_create()` 返回并
  `boot_state_advance()` 打印**之后**才注册 `g_l1_entry_pid`，而 launcher
  内核线程此时已就绪——该窗口内一次定时器抢占使 ush 在 pid 存在之前跑到
  首个系统调用，L1_READY 一次性钩子 pid 比对失败，splash 钩子吞掉整个
  横幅与首个提示符（ush 本体健康地等待输入）。
- **三层修复**：(1) 根因——创建 + 注册收进同一段关中断窗口（单 CPU 设计
  中定时器 IRQ 是唯一抢占源）；(2) 第二道防线——`g_l1_entry_pid==0`
  期间任意 pid 的首个系统调用触发一次性钩子；(3) 症状层——uname 操作
  改为与 LANG_GET 同形的纯缓冲填充（横幅路径不再有 kcap 控制台捕获）。
- **验收**：默认 splash 启动（竞态主场）连续 **20/20** 横幅真实版本串、
  `uname -r` 精确、`uname -a` 完整、零 panic。
- 证据：`evidence/wp-severe-fix-and-closure/b-k08-uname-race.md`。

## ③ K-09：E2E 测试失败"沙箱网络"误诊（以计数器推翻）

- **网络栈以自身计数器证明健康**（netstat：DHCP 已服务、ARP 1 应答、
  ICMP 4/4、TCP 1、明文 HTTP 下载保存 24 字节）+ 一次**真实 TLS 1.2
  DHE-RSA-AES128-SHA256 会话**（加密 GET 已服务、close_notify 双向观察）。
- **真缺陷四个**：(1) 一次性 TLS 测试服务器死于内核 TLS1.3 优先 hello
  （服务器现循环 accept 到一个完整会话）；(2) `-serial mon:stdio` 台架
  通道在本沙箱可测地饿死 QEMU 主循环（同 ISO 在 unix-socket 串口下 ping
  4/4——两个 E2E 运行器全部改走 unix-socket）；(3) 陈旧提示符匹配把下一条
  命令射进仍在执行的命令；(4) **真实内核缺陷——COM1 RX 边沿丢失窗口**
  （16550 在 8259 边沿触发输入后面电平保持 INTR，突发落进服务窗口不再
  产生新边沿，剩余字节滞留 FIFO——粘贴的长命令行整行丢失）：以 10 ms
  tick 兜底 RX 轮询修复。
- **验收**：HTTPS E2E **8/8**、SSH E2E 出站场景 PASS（ssh-auth + ssh-exec）。
  入站 sshd（宿主 paramiko → 客内 sshd）是唯一余留边界（pcap + monitor
  转储 + TX-errors 计数器证据，KNOWN_ISSUES 诚实记录）。
- 证据：`evidence/wp-severe-fix-and-closure/b-k09-e2e-network.md`。

## ④ K-10：OCIRE UEFI 轨单字符 '!' 之死（关闭）

- **根因**：`tools/build_ocire_iso.sh` 把 `build/ocbl/ocbl_x64.efi`（入口
  RVA 是 post-EBS 裸入口，期待 RCX=handoff/RDX=魔数）直接当作 BOOTX64.EFI
  摆放——OVMF 的 StartImage 以 EFI ABI 到达，OCBL 入口即死，串口只留一个
  '!'（ABI 违例标记）。修复：恢复盘 ISO 摆放主 ISO 的链条
  （BOOTX64.EFI = OCRMECL PE、/OCBL.EFI = OCBL、El Torito = OCRMECL 复合）。
- **验收**：OCIRE 电池 **14/14**——七个 UEFI 场景全绿，为该电池存在以来
  首次。
- 证据：`evidence/wp-severe-fix-and-closure/b-k10-ocire-uefi.md`。

## ⑤ update 全链路（L1 程序 → 网络下载 OTA → A/B 槽位 → 刷写）

- **全链电池 `tools/abchain_e2e.py`（unix-socket 串口）10/10**：GRUB 自举
  A/B 盘从槽 A 启动 → `dhcp` → `config set update_url` → `update
  --status`（current boot: A / A/B disk: present）→ L1 `update` 向导五步
  （网络 → A/B 盘 → **IP 字面量直解** → manifest → 确认安装：下载
  1387 KB → SHA256 验证 → 解包刷入 B 槽 → set boot B → "reboot
  required"）→ 确认重启 → **BOOT_SLOT=B + 包内核横幅 + `uname -r` 包版本
  + `update --status` current/next boot: B（确认提升）**。
- **宿主侧字节铁证**：刷写后 B 槽 `/boot/opencube.elf` 与包内
  `kernel/opencube.elf` sha256 逐字节一致，A 槽与种子内核一致。
- **链上抓到并修复的真断点四个**：(1) 向导 DNS 门拒绝 IP 字面量服务器
  （`net_cmd_dns` 现直解 IP 字面量）；(2) 测试 manifest 字段名与生产格式
  漂移（`sha256` vs 生产 `package_sha256`——电池现在以生产字段名从真实
  包重生成 manifest，永久盯防此类漂移）；(3) `dhcp` 违反 RFC 2131——单发
  DISCOVER + ~500 ms 窗口把健康局域网约 8 次启动 1 次报成超时（DISCOVER
  与 REQUEST 现各重传 3 次 × 800 ms 墙钟）；(4) **OTA 下载空窗中断**——
  `net_recv` 内部仅等 ~1.5 s 无数据即返回 -1，下载循环 `n<=0` 立即放弃
  （1.4 MB ≈ 350 个窗口，任一空窗全盘报废，本电池两轮一遇）：现以
  **30 s 无进展期限**持续重试（header 与 body 双阶段、TLS 与明文双路径，
  死连接仍在期限处诚实退出、永不挂死）。
- 证据：`evidence/wp-severe-fix-and-closure/b-update-chain.md` +
  `release/update-chain-transcript.txt`（完整成功串口日志）。
