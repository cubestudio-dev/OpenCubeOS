# Chinese layer: encoding, fonts, and the system IME

Open Cube OS renders Chinese from bootloader-stage OCBL (no - Chinese
starts in the kernel console) through the recovery kernel OCIRE, with
one shared font lineage and three consumers. The pieces:

- **encoding** (`ocos/services/encoding/`) - GB2312 <-> UTF-8
  conversion, kernel-only mechanism;
- **font** (`ocos/services/font/`) - the 8x16 ASCII engine, the 16x16
  CJK engine, and the 11k-line bitmap data;
- **display cat 14** - the console/locale/IME ring-3 ops;
- **the system IME engine + session protocol** (`svc_display_ime_*`).

The CJK capability is **unconditionally compiled in** - the old
`CONFIG_TUI`/`CONFIG_CHINESE` knobs were deleted with the L0 TUI
plane.

## Encoding: GB2312 and UTF-8 (`svc_encoding_core.c`)

Internal representation is the Unicode BMP codepoint (u32). The GB2312
mapping runs **through the embedded font's reverse tables**
(`chinese_font_lookup` / `chinese_font_index_to_unicode`) "so the
encoder/decoder and the renderer always agree on the same charset" -
the font data is the single source of truth for what characters
exist. UTF-8 is decoded strictly per RFC 3629: overlongs, surrogates,
>U+10FFFF and truncation are all rejected.

```c
typedef enum encoding_kind {
    ENC_ASCII  = 0,   /* only 0x00..0x7F bytes present               */
    ENC_GB2312 = 1,   /* GB2312 double-byte + ASCII single-byte      */
    ENC_UTF8   = 2,   /* RFC 3629 UTF-8                              */
    ENC_MIXED  = 3    /* valid for >1 of the above / undecidable     */
} encoding_kind_t;

#define ENC_E_INVAL   (-2)   /* NULL pointer / zero capacity          */
#define ENC_E_TRUNC   (-3)   /* input ends mid-sequence               */
#define ENC_E_ILLEGAL (-4)   /* byte sequence not valid in the charset */
#define ENC_E_NOSPACE (-5)   /* output buffer too small               */
#define ENC_E_UNMAP   (-6)   /* codepoint has no mapping in the target */
```

API surface: per-char `encoding_gb2312_decode/encode` and
`encoding_utf8_decode/encode`; bulk `encoding_convert` (ASCII/UTF-8
byte-wise, GB2312 via the font tables; mixed input treated as
GB2312); the heuristic `encoding_detect` (pure-ASCII -> ENC_ASCII;
strict UTF-8 with >= 1 multibyte -> ENC_UTF8; GB2312 lead/trail
ranges -> ENC_GB2312; else ENC_MIXED); `encoding_status` (call
counters + charset coverage). The ring-3 face is display ops 9/10
(`encoding`, `encoding-test`).

## Fonts: generation and the engine registry

Three generated assets, three generators:

- `ocos/kernel/core_console_font_data.c` - the 8x16 ASCII table
  (`const u8 screen_font8x16[256][16]`, bit 7 = leftmost pixel),
  regenerated by `tools/gen_font.py`.
- `ocse/chinese/chinese_font_data.c` - the CJK 16x16 GB2312 bitmap
  data, generated by `tools/gen_chinese_font.py` (Unifont-derived).
  This file is the **font lineage root**: OCIRE's
  `ocire/generated/ocire_cn_font_data.c` is generated *from* it by a
  sed include-rewrite rule in `ocire/ocse.mk`, so font re-vendorings
  flow into the recovery kernel automatically (WP06g3-4.8). The
  vendoring PRESERVE list exists so a re-vendor can never restore the
  v1.0.0 baseline-clipped glyphs (WP06f).
- `tools/gen_font_gz.py` - the compressed-glyph pipeline.

The engine registry (`svc_font_engine.h`) is a WP-01 L1 extension
point:

```c
typedef struct screen_font_engine {
    const char* name;
    const u8* (*lookup)(struct screen_font_engine* self, u32 cp);
    u32 glyph_w;
    u32 glyph_h;
    /* Optional: list of code points the engine claims to support. NULL = all. */
} screen_font_engine_t;

int l1_ext_register_font_engine(screen_font_engine_t* engine);
screen_font_engine_t* l1_ext_font_engine_by_name(const char* name);
screen_font_engine_t* l1_ext_default_font_engine(void);
```

The default engine serves glyphs from the built-in 8x16 table; the CJK
engines register next to it. The console's mixed-width renderer
(`render_chinese_init` + `console_cn_init` in kmain) picks 16x16 cells
for GB2312 codepoints and 8x16 for ASCII. Consumers: display (the
console path), tui (every page), sysapi (`sys_write`'s UTF-8 wide-cell
fallback), OCSE and OCIRE (their own vendored/generated copies).

## Locale and the serial encoding

- `lang [en|zh]` (display op 4) switches the live console locale;
  state persists as the key `shell.lang` in `/etc/opencube.conf`
  (data compatibility); `disp_lang_set_str` accepts exactly "en"/"zh",
  anything else = en.
- **`L1SVC_DISP_LANG_GET` (op 16) emits exactly `en` or `zh`** (no
  newline) - this is the probe every ring-3 app's i18n runtime calls
  (`i18n_lang_zh()`, per `tr_()` call, no static cache - the #136 fix
  so `lang zh` takes effect immediately in long-running apps;
  [private-headers.md](private-headers.md)).
- `serial_encoding [utf8|gbk]` (op 17, WP06g3) - the single setting
  every console byte's COM1 tee follows; the OCSE CLI carries the same
  command for the installer world.
- `font` / `font-test` (ops 7/8) dump engine coverage and render
  glyph matrices through render_cn; `chinese` / `chinesetest` (ops
  5/6) the console CJK path.

## The system IME and the session protocol (WP06g2)

One pinyin engine serves the whole system - editors drive it
**per keystroke** instead of embedding their own. The ring-3 ops:

```c
#define L1SVC_DISP_IME        11   /* ime [-i]                */
#define L1SVC_DISP_IME_TEST   12   /* ime-test                */
#define L1SVC_DISP_IME_BEGIN  13   /* ime session open        */
#define L1SVC_DISP_IME_KEY    14   /* ime session key feed    */
#define L1SVC_DISP_IME_END    15   /* ime session close       */
```

`IME_BEGIN`/`IME_END` reset the session (out: ""). `IME_KEY`'s arg is
one decimal key code; the out's **first line is the action digit**,
the remaining lines are text:

| Action | Meaning | Caller behavior |
|---|---|---|
| `0` | not IME business | handle the key locally |
| `1` | preedit strip updated | redraw the compose strip |
| `2` | committed | insert the UTF-8 text at the cursor |
| `3` | committed + caller handles key | insert and also process the key |
| `4` | service failure / malformed protocol | **swallow the key, never leak it into the file** (postmortem disaster 6) |

`ime -i` (interactive compose line) routes DIRECT - live `\r`
redraws, same live-output rule as sshd and the TUI ops
([tui-engine.md](tui-engine.md)). The pinyin data itself is generated
(`svc_display_pinyin_data.c`, phrase table from
`tools/gen_pinyin_phrase.py` over `tools/ime_phrases.txt`).

### The editor bridge (the protocol's main client)

`editor_core.h`'s `unano_ime_feed(key)` calls `DISPLAY/IME_KEY` with
the decimal key code as the arg string; F2 (key code 0x91) toggles
via `IME_BEGIN`/`IME_END`; the preedit strip is the 160-byte
`unano_strip`; action 4 exists specifically so a failing service can
never corrupt the edited file. The TUI desktop's editor and terminal
use the same engine. User guide:
[../manual/chinese-console.md](../manual/chinese-console.md).

## The three-world picture

| World | Chinese capability | Source of the font |
|---|---|---|
| OCOS (main kernel) | mixed-width console + TUI + IME + encoding service | `ocos/services/font/` (from the same lineage) |
| OCSE (installer) | console_cn + render_cn + encoding, bilingual GUI/wizard | `ocse/chinese/chinese_font_data.c` (the lineage root, regenerated by `tools/gen_chinese_font.py`) |
| OCIRE (recovery) | console_cn + bilingual shell help (`lang [en\|zh]`) | `ocire/generated/ocire_cn_font_data.c` (generated from OCSE's copy) |

OCBL itself is ASCII-only by design (the 512-byte stage1 budget and
the El Torito constraints leave no room for CJK glyph tables in the
loader).
