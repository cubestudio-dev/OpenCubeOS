L1SVC interface dictionary ​

The complete, authoritative listing of the L1SVC ring-3 service-call surface: 20 categories, 208 numbered operations, reached through the single syscall SYS_L1SVC (110). This page merges the kernel-side numbering header (ocos/services/sysapi/interface/svc_sysapi_l1svc.h, 461 lines), the auto-generated ring-3 mirror (ocos/interface/l1svc_ops.h, produced by tools/gen_l1svc_ops.py), and the per-family op tables verified in the service sources. Structs and defines below are copied verbatim.

Companion pages: the syscall ABI itself is documented in syscall-reference.md; how to add a new service or op is writing-services.md; the call path through core_kcap is dissected in call-chains.md.

1. Protocol ground rules ​

Every rule below is stated as trigger -> processing -> impact; each one is load-bearing and verified in source.

1.1 The call shape ​

c
static inline long syscall5(long n, long a, long b, long c, long e, long f) {
    long r;
    register long r10 __asm__("r10") = e;
    register long r8  __asm__("r8")  = f;
    __asm__ volatile("int $0x80"
                     : "=a"(r)
                     : "a"(n), "D"(a), "S"(b), "d"(c), "r"(r10), "r"(r8)
                     : "memory");
    return r;
}

(the ring-3 helper from ocos/interface/l1_lib.h; the typed wrapper sys_l1svc(cat, op, arg, out, cap) calls syscall5(SYS_L1SVC, cat, op, arg, out, cap)):

  • Trigger: a ring-3 program wants one service operation. It never links against kernel code; the only door is int 0x80 with rax=110 and the five arguments in rdi, rsi, rdx, r10, r8 (the 5th argument rides in r8, stashed by the entry path into core_syscall_arg5() before the handler runs).
  • Processing: sys_l1svc() in ocos/services/sysapi/src/svc_sysapi_syscall.c copies arg into a kernel buffer, routes cat through L1SVC_CAT_NAME(cat) to the owning service's l1_dispatch(op, arg, out, cap), captures the rendered text, and copies it back.
  • Impact: the caller receives a NUL-terminated plain-ASCII text block in out; the kernel's return value says only whether the call routed, never whether the operation "succeeded" (see 1.5).

1.2 Buffer limits ​

LimitValueWhy
cap (out capacity)1..32768raised from 8192 in WP06g2 so help -a fits the full 284-program bilingual registry listing

1.3 Interrupt state around dispatch ​

  • Trigger: an op body may contain device-wait loops (disk settle, DHCP timeouts, audio polling) that are tick-driven.
  • Processing: sys_l1svc() executes __asm__ volatile("sti") before svc_framework_dispatch(...) and __asm__ volatile("cli") after it (the v2.0.0 "group N" fix).
  • Impact: op bodies can sleep/yield on the scheduler tick and still return through the syscall path; without this the first long op would freeze the machine instead of the caller.

1.4 The text-anchor contract ​

  • Trigger: any consumer - a shell script, the mega-app wizards, the E2E regression gates, tools/gen_api_docs.py - needs to read an op's output programmatically.
  • Processing: every op renders plain ASCII English text, line oriented, with stable key substrings ("A/B disk: present", "New version available.", "DHCP success", "DNS resolution failed", "reboot required", "Current version is up to date.", "IP:"). wiz_find()/wiz_token_after() in ocos/interface/wizard_lib.h parse exactly these anchors; the ring-3 side formats nothing.
  • Impact: service output strings are ABI. Changing a rendered sentence breaks wizards and release gates the same way a renumbered op would - English output lines are the frozen contract (see also the interface-freeze rules in ../root/CONTRIBUTING.md).

1.5 Return-code semantics ​

  • Trigger: the op completed (or failed) and sys_l1svc returns.
  • Processing: the service's own non-zero exit status is not propagated as a syscall error. Only an unrouteable category/op (or an empty out buffer with rc < 0) returns -1; everything else copy_to_users the NUL-terminated text and returns 0.
  • Impact: failure reporting lives inside the text ("...: FAILED (...)", "usage: ..."), which is why the anchors above are the contract, and why the ring-3 wrapper (l1svc_main()) prints "<name>: " tr_("svc_call_failed") only on rc != 0 (i.e. only on routing failures).

1.6 Numbering discipline ​

  • Trigger: a new operation is needed.
  • Processing: a new #define L1SVC_<CAT>_<NAME> <next> is appended to svc_sysapi_l1svc.h; tools/gen_l1svc_ops.py regenerates the ring-3 mirror; the ush-side constant block is a verbatim copy.
  • Impact: renumber only by appending. Existing numbers are frozen ABI: cat 18 ("ocire") is additionally frozen against ocire/agent/ocire_agent.c, which compiles against the numbers as an ABI, not a source dependency.

1.7 The three routing styles ​

How an op's text gets into out (decided per op in the family dispatcher):

  1. captured - core_kcap_run_fn(fn, arg, out, cap): the op body is an old shell-command body that prints via screen_console_puts; while a capture is active the capture hook IS the console hook (one slot), characters are collected into out, framebuffer draw and the serial tee are suppressed, captures stack to 4 levels, overflow is marked never silently truncated. One-shot text ops.
  2. direct - out[0]0; return fn(arg);: live console sessions (sshd, all 9 TUI ops, ime -i, power sleep); the op's own console output is the session, the serial tee mirrors it verbatim, out stays empty.
  3. buffer-render - the dispatcher writes into out with its own put() helpers (l1, klog, health, diag, fs, time, watchdog dispatchers).

A documented field note: tui-test was first routed captured, but its ~4.4 KiB verdict block overflowed the 4096-byte SVC result buffer used at the time and truncated the final summary, so it went direct. power sleep and sshd route direct because running them captured swallowed every live console line during the park (found live during an OCIRE-supervised boot).

5. Ring-3 consumption patterns ​

The standard wrapper body (about 150 of the 284 programs are exactly this):

c
#include "l1_lib.h"
#include "l1svc_ops.h"
int app_main(int argc, char **argv)
{ return l1svc_main(argc, argv, L1SVC_CAT_X, L1SVC_X_OP); }

l1svc_main() (in ocos/interface/l1_lib.h):

  • joins argv[1..] with single spaces into a 256-byte argument line (so multi-word grammar arrives exactly as typed),
  • calls sys_l1svc(cat, op, arg, out, 32768) with a static 32 KiB BSS buffer (a 4096-byte stack buffer once truncated help -a),
  • prints out plus the missing trailing newline; on rc != 0 prints "<name>: " tr_("svc_call_failed").

Interactive apps (wizards, TUI, editors, logcat -f, health watch) layer SYS_READLINE/SYS_GETCH on top; the wizard anchor helpers (wiz_find, wiz_token_after) parse the captured English text per 1.4. See ../l1/writing-apps.md and ../l1/wizard-library.md.

6. Dispatch plumbing recap ​

  • Trigger: SYS_L1SVC reaches svc_framework_dispatch(cat, op, arg, out, cap).
  • Processing: the collector table s_svcs[64] (filled at boot by svc_framework_collect() from the .oc_svcs linker section, boundaries __oc_svcs_start/_end from linker.ld) is scanned for an exact category-string match; a matched service with a NULL l1_dispatch is "kernel-only" and returns -1, otherwise the service's l1_dispatch(op, arg, out, cap) runs.
  • Impact: exactly one service owns each category string (the declared exception: "ocire" is implemented by services/ocembed/); the boot ORDER stays the hand-curated kmain composition-root sequence - the collected table is only the identity/dispatch surface. See writing-services.md for the full add-a-service walkthrough.
