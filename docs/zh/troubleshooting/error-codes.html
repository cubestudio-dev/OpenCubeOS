错误代码 — 完整的数值面 ​

Open Cube OS 没有全局 errno 也没有 errno.h — freestanding 内核不链接 libc。通用约定是：

  • 0 = 成功，负数 = 失败（-1 为通用；Returns 0 on success, -1 on failure 是文档化习语）。
  • 需要精度的子系统使用稠密负数枚举 — 8 个家族， 共 61 个代码，下文逐一列出其触发场景与应对。
  • 尺寸/长度返回 -1；环形缓冲读取越过窗口返回 -1； watchdog 槽位 API 返回 -1（表满）/ -2（参数错误）。
  • 唯一的正数哨兵家族是崩溃来源伪向量 OC_CRASH_SRC_* (32..36)，它们搭载在 crashlog 记录的 vector 字段上。

本页涉及的命令：dmesg、 logcat、logctl、 crashlog、health、 update、config。

家族 1 — OC_UPDATE_E_*（15 个代码，更新管线） ​

定义于 services/selfhost/interface/svc_selfhost_update.h；在 svc_selfhost_ab.c / svc_selfhost_update.c 中解码为文本。这些是 每条 update: ... failed: <why> 行背后的代码。

代码值含义触发场景应对
OC_UPDATE_E_CONFIG-1配置文件缺失或不可读/etc 卷上没有 /etc/opencube.conf检查 config path；/etc 卷是否已挂载？见 storage-issues.md
OC_UPDATE_E_PREFIX-2URL 前缀非法（必须为 http:// 或 https://）update_url 拼写错误（ftp://...）config get update_url，用 config set update_url http://... 修正
OC_UPDATE_E_DNS-3DNS 解析失败更新主机无法解析dns <host>；从 dhcp/ip 输出检查 DNS 服务器
OC_UPDATE_E_CONNECT-4连接失败服务器不可达（路由/防火墙）ping 该主机，route 查看网关，firewall 列表
OC_UPDATE_E_TIMEOUT-5无响应（超时）服务器未接受任何内容重试；检查主机可达性
OC_UPDATE_E_HTTP-6HTTP 错误服务器返回错误状态检查服务器端 / URL 路径
OC_UPDATE_E_JSON-7JSON 解析失败update.json 格式错误用 wget 手动获取并阅读
OC_UPDATE_E_BUFSIZE-8响应过大changes 列表溢出 128 字节缓冲服务端修复（缩短 changes）
OC_UPDATE_E_DISABLED-9配置中 online_update=no更新被配置禁用config set online_update yes
OC_UPDATE_E_NOAB-10无 A/B 磁盘未从 A/B 布局启动update status，然后创建：abdisk <dev>（destructive）
OC_UPDATE_E_SHA-11SHA256 校验失败包损坏或被篡改重新下载；检查 update.json 中的 package_sha256
OC_UPDATE_E_TARGZ-12包不是有效的 gzip/tar下载被截断重新下载；核对大小
OC_UPDATE_E_IO-13文件系统 I/O 错误/data 写入失败df，对卷执行 fsck
OC_UPDATE_E_SLOT-14槽位非法（应为 A 或 B）内部槽位运算失败运行 abcfg；若持续出现则报告
OC_UPDATE_E_ARGS-15NULL / 畸形参数内部调用方 bug附确切命令行报告

家族 8 — OC_POWER_E_UNSUPPORTED（1 个代码） ​

services/power/interface/svc_power_core.h（+ ocse 孪生）：-1 — "走完所有端口后机器仍在运行"。当关机遍历尝试了每个端口 （ACPI S5、端口 0x64、CF9）而机器仍活着时返回；用户看到 Power off not supported. System halted. — 在 VM 中请使用 宿主机的电源控制。

解码文本表（字符串所在处） ​

每个家族在调用点旁都有孪生的解码到文本表 —— 天然的 grep 锚点：svc_selfhost_ab.c（update）、 svc_crypto_x509.c（x509）、fs/block/net 服务中的 put() 字符串。SMBus i801 状态字解码为 NACK/device error、 bus error/collision、transaction failed、timeout。

统一 panic 横幅（打印内容，按序） ​

在串口（权威）+ VGA（尽力而为）上：

  1. *** NESTED PANIC INSIDE PANIC - HALTING *** — 一行，然后停机 （绝不递归）。
  2. #DF 特例：*** KERNEL PANIC: <reason> [task=<name>] *** + source: #DF Double Fault err=0x<hex> rip=0x<hex> handled at dispatcher depth] + core dump: skipped in #DF mode (see KNOWN_ISSUES) + 策略行。
  3. CR3 规范化；klog 环形 FATAL 记录；crashlog 记录（无文本）。
  4. *** KERNEL PANIC: <reason> ***（+ [KERNEL STACK OVERFLOW: exhausted, task=<name>] 注记）+ 内核版本/构建 + 来源 行（manual/panic|watchdog-timeout|assertion-failed|contained(TUI)| kstack-overflow|exception <N>）+ 任务 + 寄存器 + 回溯。
  5. VGA 单行（原因截断到 90 字符）+ Registers and call trace on the serial console.
  6. 核心转储状态：core dump: UNAVAILABLE (no boot-time buffer) 或 <N> bytes captured, persisted to /var/crash/core.dump（或串口 回退 / persist FAILED）。
  7. L1 panic 处理链：*** panic handler claimed recovery - resuming ***（罕见 — TUI 崩溃防护是唯一用户）。
  8. 日志刷写状态：crash log: <n> bytes to /var/log/crash.log; klog flushed <n> bytes to /var/log/kernel.log（或 FAILED 变体）。
  9. 策略：policy: HALT|REBOOT - system stopped (safe halt loop)| - rebooting NOW。

日志格式 — 解读输出 ​

klog（dmesg / logcat） ​

[<seconds>.<mmm padded to 3>] <LEVEL padded to 6> <module>: <message>

示例：[ 12.345] ERROR watchdog: watchdog slot 3 (net-rx) -> KILL task。

级别：DEBUG 0、INFO 1、WARN 2、ERROR 3、FATAL 4。环形 容纳 1024 条；覆盖计入 klog_dropped()， dmesg 显示页脚 -- <shown> lines (ring <n>/1024, dropped <d>) --。用 logcat -l <level>（debug..fatal 或 0-4）、-m <module>、-k <keyword>、-t <seconds>、-n <count> 过滤； -f 跟随。级别过滤陷阱见 silent-failures.md。

引导阶段日志 ​

[HH:MM:SS.mmm] <stage>: OK|FAIL

安静级别 1 抑制非 FAIL 行；任何 FAIL 子串都为引导状态 判定标记失败。阶段名（OCST 阶梯）： BOOT、KM_AIN_ENTERED、SCHED_READY、DRIVERS_READY、 SERVICES_READY、L1_LAUNCHED、L1_READY，运行时标记 255 = RUNTIME。

健康告警（klog WARN 类） ​

alarm: memory >90% used (<used>/<total> KiB)
alarm: <n> active tasks (>64)
alarm: CPU >=90% busy for 10 consecutive seconds

机器"感觉不对"时第一个要运行的就是 health 命令 — 见 silent-failures.md。

崩溃记录 ​

crashlog 列出 32 条环形记录（字段：jiffies、rtc_epoch、vector、 ring、error_code、rip、rsp、cr2、tid、pid、task[16]）；刷写到 /var/log/crash.log；核心转储落在 /var/crash/core.dump；klog 刷写到 /var/log/kernel.log。
