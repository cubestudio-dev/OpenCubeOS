隐藏命令与测试桩 — 调试面 ​

284 个已注册程序中约三分之一是测试桩：主体从 v2.2.0 shell 迁移而来，现在经由 L1SVC 桥接提供服务，或以平坦 ring-3 探针形式链接。它们都是普通的注册表命令 —— 在 ush> 提示符下输入名字并按 ENTER 即可；无需特殊运行器， 除非特别说明也无需 flag。help 中没有任何标记表明它们是测试： 它们与 ls 或 ping 一样出现在 A-Z 列表中。

全仓扫描统计出 约 93 个测试味程序：69 个 *test* 命名的 目录应用外加 24 个平坦单文件探针（边界是模糊的 —— hello、loop、badapp、p0leak 是作业测试用作目标的平坦工具 探针）。本页逐一列出，按其演练的内容分组，附运行方法与健康 运行的输出。

安全性：除标注项外，此处一切均为只读或自包含 除 标注项之外：fs_mount_test（格式化设备）、四个电源路径 探针（可能终结会话）、crashtest（故意让内核 panic —— 这就是测试本身）、stackovf/badapp/sigsegv_test（故意 自杀）。

它们如何接线 ​

  • 目录桩（ocos/l1apps/<name>/main.c）是标准 l1svc_main() 封装：argv 被连接成一条 256 字节行并发送给 所属服务 op；服务运行真正的测试主体，打印文本经输出捕获 返回。
  • 平坦探针（ocos/l1apps/<name>.c|.asm，标签 l1）是真实 的 ring-3 程序，自己发起原始系统调用 —— 它们直接演练 内核面并打印各自的判定。
  • 判定行统一为 PASS / FAIL / SKIPPED（硬件缺失时为 (honest skip) / (honest FAIL) —— 那是正确的结果， 不是失败）。

msitest — MSI 真实注入（op 21，diag 服务） ​

msitest 是唯一会在你的真实硬件上触发真实中断的桩。 三个步骤，按序执行（svc_diag_l1.c）：

  1. LAPIC 存在性 + self-IPI — 在向量 0x50 上注册处理程序， 经确切的消息写路径发送 self-IPI，短暂自旋， 然后比较向量计数器：self-IPI vector 0x50: fired N time(s) PASS。
  2. MSI 能力设备普查 — 遍历 PCIe 设备列表统计 cap_msi || cap_msix：MSI-capable devices: N of M。
  3. 真实触发 — 找到第一块 e1000，在向量 0x51 上武装 MSI， 启用设备，然后向 Interrupt Cause Set 寄存器（BAR0 + 0x00C8）写入 0xFFFFFFFF 以一次性强制 所有中断原因。必须落下一次真正的 MSI 消息写：e1000 MSI fire (ICS->MSI): fired N time(s) PASS。随后解除 MSI 并 注销向量。无 e1000 或无 MSI 能力/BAR0 → SKIP (reported honestly)。

最终判定：msitest: PASS / msitest: FAIL。若步骤 3 失败而 步骤 1-2 通过，则是 MSI 路由（而非 LAPIC）损坏 —— 先查 pcibars 的 BAR0 映射与 pcie 的链路状态。

crashtest — 8 种故意失败模式 ​

crashtest <mode> 注入一次特定崩溃，以便你观察完整的 WP-11 恢复路径（转储 + crashlog + klog 刷写 + 策略）。可以通过 裸命令或 sysdiag classic/direct 分发触达 —— 刻意不设为 向导按钮（"为故意 panic 注入设一个向导按钮是个坑"）。

模式行为应当看到
panic直接调用 kernel_panic()*** KERNEL PANIC: manual crashtest: kernel_panic() *** + 寄存器 + 回溯 + 策略行
exc执行一条 ring-0 #UD异常横幅，随后 panic 路径；crashtest: #UD returned unexpectedly 表示故障未被触发 —— 本身即失败
pf在 ring 0 写未映射地址ring-0 exception 14 (#PF Page Fault) panic
assertOC_ASSERT(0)panic 原因 assertion failed: 0
wd强制软件 watchdog 超时（武装 + 心跳回拨）watchdog timeout: ... panic
ovf孵化一个逐帧增长 4 KiB 直至守卫页的 kthreadKERNEL STACK OVERFLOW (guard page hit, task=...) panic
dumpcore_dump_save("manual crashtest dump") — 不 panic转储已写入；启动期缓冲缺失时 crashtest: dump FAILED (no boot-time buffer)
policy halt|reboot设置 panic 后动作crashtest: policy set - after the next panic the kernel will HALT

未知变体打印 crashtest: unknown variant '<v>' (try: crashtest help)。任意 panic 模式之后，验证记录已落盘：crashlog （32 槽环形）、dumpinfo（核心转储缓冲）、dmesg（klog FATAL 行），以及文件系统上的 /var/log/crash.log + /var/crash/core.dump。

从脚本运行桩 ​

每个桩都是普通命令，因此通常的 shell 特性都适用：

ush> memtest > /tmp/mem.txt
ush> run dnstest
ush> sysdiag direct memtest        # the mega-app verbatim door
ush> logcat -k msitest -f          # follow only msitest's klog lines

E2E 套件在串口控制台上做的正是这些（见 ../dev/e2e-suites.md）；逐应用记录 （tools/run_l1_per_app.py）为每个程序启动一次 ISO 并通过 run <name> 运行它。
