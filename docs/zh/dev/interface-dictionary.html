L1SVC 接口字典 ​

L1SVC ring-3 服务调用面的完整权威清单：20 个类别、208 个 编号操作，经唯一系统调用 SYS_L1SVC（110）到达。本页合并 内核侧编号头文件 （ocos/services/sysapi/interface/svc_sysapi_l1svc.h， 461 行）、自动生成的 ring-3 镜像 （ocos/interface/l1svc_ops.h，由 tools/gen_l1svc_ops.py 产出），以及在服务源码中核验过的 各家族 op 表。下述结构体与宏为原文照录。

配套页面：系统调用 ABI 本身见 syscall-reference.md；如何添加新 服务或 op 见 writing-services.md；经 core_kcap 的调用路径在 call-chains.md 中解剖。

1. 协议基本规则 ​

下列每条规则都以 触发 -> 处理 -> 影响 的方式陈述；每一条 都是承重的且在源码中核验过。

1.1 调用形状 ​

c
static inline long syscall5(long n, long a, long b, long c, long e, long f) {
    long r;
    register long r10 __asm__("r10") = e;
    register long r8  __asm__("r8")  = f;
    __asm__ volatile("int $0x80"
                     : "=a"(r)
                     : "a"(n), "D"(a), "S"(b), "d"(c), "r"(r10), "r"(r8)
                     : "memory");
    return r;
}

（来自 ocos/interface/l1_lib.h 的 ring-3 辅助函数；类型化 包装 sys_l1svc(cat, op, arg, out, cap) 调用 syscall5(SYS_L1SVC, cat, op, arg, out, cap)）：

  • 触发：一个 ring-3 程序想要一次服务操作。它从不链接 内核代码；唯一的门是以 rax=110、五个参数位于 rdi, rsi, rdx, r10, r8 的 int 0x80（第 5 参走 r8， 入口路径在处理函数运行前把它暂存进 core_syscall_arg5()）。
  • 处理：ocos/services/sysapi/src/svc_sysapi_syscall.c 中的 sys_l1svc() 把 arg 拷入内核缓冲区，经 L1SVC_CAT_NAME(cat) 把 cat 路由到所属服务的 l1_dispatch(op, arg, out, cap)，捕获渲染出的文本并 回拷。
  • 影响：调用方在 out 中收到一块 NUL 结尾的纯 ASCII 文本；内核返回值只说明调用是否路由成功，从不说明操作 是否"成功"（见 1.5）。

1.2 缓冲区限制 ​

限制值原因
cap（out 容量）1..32768WP06g2 从 8192 提升，使 help -a 能装下完整 284 程序双语注册清单
arg 长度256 字节NUL 结尾的用户字符串，拷入固定内核缓冲区
OCIRE arg 长度4096 字节仅 cat 18：日志代理一次 LOG_APPEND 至多追加 4 KiB
out == 0 && cap == 0允许OCIRE 发后即忘拼法：渲染进 256 字节内核暂存缓冲区，跳过回拷（3.0.0-WP03 G4）

1.3 分发前后的中断状态 ​

  • 触发：op 体可能包含 tick 驱动的设备等待循环（磁盘 稳定、DHCP 超时、音频轮询）。
  • 处理：sys_l1svc() 在 svc_framework_dispatch(...) 之前执行 __asm__ volatile("sti")、之后执行 __asm__ volatile("cli")（v2.0.0 的 "group N" 修复）。
  • 影响：op 体可以在调度器 tick 上睡眠/让出并仍经系统 调用路径返回；没有这一点，第一个长 op 会冻住整台机器 而不是只冻住调用方。

1.4 文本锚点契约 ​

  • 触发：任何消费者 —— shell 脚本、mega 应用向导、E2E 回归门禁、tools/gen_api_docs.py —— 需要以编程方式 读取一个 op 的输出。
  • 处理：每个 op 渲染纯 ASCII 英文文本，面向行，带 稳定的关键子串（"A/B disk: present"、"New version available."、"DHCP success"、"DNS resolution failed"、 "reboot required"、"Current version is up to date."、 "IP:"）。ocos/interface/wizard_lib.h 中的 wiz_find()/wiz_token_after() 解析的正是这些锚点； ring-3 侧不做任何格式化。
  • 影响：服务输出字符串就是 ABI。改动一句渲染出的句子 对向导与发布门禁的破坏与重排 op 编号完全等同 —— 英文 输出行是冻结契约（另见 ../root/CONTRIBUTING.md 的 接口冻结规则）。

1.5 返回码语义 ​

  • 触发：op 完成（或失败）且 sys_l1svc 返回。
  • 处理：服务自身的非零退出状态不会作为系统调用错误 传播。只有不可路由的类别/op（或 rc < 0 且 out 缓冲 区为空）返回 -1；其余一切把 NUL 结尾的文本 copy_to_user 并返回 0。
  • 影响：失败报告活在这些文本里（"...: FAILED (...)"、 "usage: ..."），这正是上述锚点是契约的原因，也是 ring-3 包装（l1svc_main()）只在 rc != 0（即只在路由失败） 时打印 "<name>: " tr_("svc_call_failed") 的原因。

1.6 编号纪律 ​

  • 触发：需要一个新操作。
  • 处理：向 svc_sysapi_l1svc.h 追加一条新的 #define L1SVC_<CAT>_<NAME> <next>； tools/gen_l1svc_ops.py 重新生成 ring-3 镜像；ush 侧的 常量块是逐字副本。
  • 影响：只允许以追加方式编号。既有编号是冻结 ABI： cat 18（"ocire"）还额外相对 ocire/agent/ocire_agent.c 冻结 —— 后者把这些编号当作 ABI 编译，而非源码依赖。

1.7 三种路由方式 ​

一个 op 的文本如何进入 out（按 op 在家族分发器中逐个 决定）：

  1. 捕获 —— core_kcap_run_fn(fn, arg, out, cap)： op 体是一个经 screen_console_puts 打印的旧 shell 命令 体；捕获激活期间捕获钩子就是控制台钩子（唯一槽位）， 字符被收集进 out，帧缓冲绘制与串口 tee 被压制，捕获 可叠至 4 层，溢出被标记、绝不静默截断。用于一次性文本 op。
  2. 直连 —— out[0]0; return fn(arg);：实时控制台 会话（sshd、全部 9 个 TUI op、ime -i、 power sleep）；op 自身的控制台输出就是会话，串口 tee 原样镜像，out 保持为空。
  3. 缓冲区渲染 —— 分发器用自己的 put() 辅助函数写 out（l1、klog、health、diag、fs、time、 watchdog 分发器）。

一条文档化的现场注记：tui-test 最初以捕获方式路由，但 其约 4.4 KiB 的结论块溢出了当时使用的 4096 字节 SVC 结果 缓冲区并截断了最终摘要，因此改为直连。power sleep 与 sshd 直连路由，因为以捕获方式运行它们会在停驻期间吞掉 每一条实时控制台行（在 OCIRE 监督启动期间现场发现）。

5. ring-3 消费模式 ​

标准包装体（284 个程序中约 150 个正是这个）：

c
#include "l1_lib.h"
#include "l1svc_ops.h"
int app_main(int argc, char **argv)
{ return l1svc_main(argc, argv, L1SVC_CAT_X, L1SVC_X_OP); }

l1svc_main()（位于 ocos/interface/l1_lib.h）：

  • 把 argv[1..] 以单空格拼成 256 字节参数行（因此多词 语法与键入时完全一致地到达），
  • 以静态 32 KiB BSS 缓冲区调用 sys_l1svc(cat, op, arg, out, 32768)（曾经一个 4096 字节栈缓冲区截断过 help -a），
  • 打印 out 加上缺失的结尾换行；rc != 0 时打印 "<name>: " tr_("svc_call_failed")。

交互式应用（向导、TUI、编辑器、logcat -f、 health watch）在其上叠加 SYS_READLINE/SYS_GETCH；向导 锚点辅助函数（wiz_find、wiz_token_after）按 1.4 解析 捕获的英文文本。见 ../l1/writing-apps.md 与 ../l1/wizard-library.md。

6. 分发管线回顾 ​

  • 触发：SYS_L1SVC 到达 svc_framework_dispatch(cat, op, arg, out, cap)。
  • 处理：扫描收集表 s_svcs[64]（启动时由 svc_framework_collect() 从 .oc_svcs 链接节填充，边界 __oc_svcs_start/_end 来自 linker.ld）寻找类别字符串 的精确匹配；匹配到但 l1_dispatch 为 NULL 的服务是 "纯内核"并返回 -1，否则运行该服务的 l1_dispatch(op, arg, out, cap)。
  • 影响：每个类别字符串恰由一个服务拥有（已声明的 例外："ocire" 由 services/ocembed/ 实现）；启动顺序 仍是手工策展的 kmain 组合根序列 —— 收集表只是身份/ 分发面。完整的添加服务流程见 writing-services.md。
