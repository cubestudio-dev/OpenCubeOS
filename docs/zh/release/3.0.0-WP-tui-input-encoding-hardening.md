# 3.0.0-WP-tui-input-encoding-hardening — TUI 输入与编码加固
输入/编码/显示加固批次：五个用户上报缺陷逐一追到根因，每一项都有
复现证据；其后对三条链路做了全量扫描。所有修复遵循"标准纪律、
零平台特判"原则。

## 变更

### 1. TUI 入口隐藏（保留注册、仅不再列出）
八个旧式 TUI 子启动器（`tui-test`、`tui-hw`、`tui-net`、
`tui-sysinfo`、`tui-time`、`tui-drv`、`tui-sys`、`tui-ext`）保持
注册且可直接执行——只是不再"列出"：`help` 与 `help -a` 不再显示，
桌面树移除了扩展实验室镜像节点，对账口径为 311 注册 / 292 列出 /
8 隐藏（呈现门禁同时断言两个数字）。未删除任何代码路径；唯一
事实源是 `l1_tui_entry_filter.c` 中的 `k_hidden[]` 表。

### 2. OCIRE 空格捕获（根因：扫描码表越界）
`lang zh` 打成 `LANGZH`、带空格命令全部失效：PS/2 扫描码解码器
查表越界一格——空格键的通码（0x39）落表外，把相邻内存当作 ASCII
映射读出。在表上修复；六路径矩阵（OCIRE 与 OCOS × 串口、PS/2、
UEFI）全绿，含 `LANG ZH`、`LANG EN` 与所有带空格命令。

### 3. 跨写入 UTF-8 TTY
ush 行编辑器对每个按键事件做单字节 write 回显；粘贴或输入法上屏
的汉字以 3-4 个这样的写到达，而控制台路径对每个写独立解码——
孤立前导字节被按 Latin-1 画格，每个汉字都回显成实心方块，直到
整行重绘才偶然修复。TTY 现在跨写重组多字节序列
（`core_tty_utf8.c`）：接收与回显字节精确；`cat` UTF-8 文件返回
精确序列；退格删整个字符（线上可见 2 格擦除）；80 格换行不切分
字形；步进按"字符"计。证据含 VLM 读屏的 VGA 截图与原始字节
hexdump。明确不做（维持设计边界）：输入法、locale 体系、文件名
规范化。

### 4. 串口编码方向（裁定，无代码变更）
两条串口路径的原始字节捕获：内核输出全部为合法 UTF-8，OCBL 只发
纯 ASCII + 标准 ANSI CSI（与 GRUB 串口菜单相同的序列），内建
`serial_encoding=gbk` tee 双向转换正确。上报的"COM1 乱码"是宿主
终端解码所致——报告者的 Windows 宿主运行 windows-936（GBK）代码页
读 UTF-8 流。登记，非代码缺陷。

### 5. VMware 三重故障修复（五项发现、四项代码修复）
交付的 `vmware.log`（15 次 `Triple fault.`，每周期约 1.24 秒）与
启动串口被推成完整推理链（逐字引用、崩溃阶段映射与假设矩阵见
`evidence/.../vmware/vmware-reasoning.md`）：

- **H1 - OCBL 核心从未装载 IDT。** 64 位核心继承了固件实模式 IVT
  状态（`{0, 0x3FF}`），长模式下任何向量化都会误读——异步事件
  升级为 #GP → #DF → 三重故障。OCBL 现在自建 256 门表
  （`ocbl_idt.c/.S/.h`）：异常上串口报告并停机，IRQ/NMI 走
  iretq；实模式蹦床在每个模式边界交换向量化纪律（下行恢复固件
  IVT、上行恢复自有表）。不依赖 VMware 的决定性证明：在纯 64 位
  OCBL 代码断点处注入 NMI，修复前构建死亡（复位路径），修复后
  构建吸收。
- **H2 - El Torito 引导驱动器号由固件自选**（报告者的 VMware 传
  0x9F 而非 0xE0+）：扫描永远看不到引导 CD，菜单回退到关机倒
  计时。现按 El Torito 类型判定。
- **H3 - 状态监视器的 EBDA 守卫读的是 I/O 端口而非 BDA 内存字**，
  因此从未触发，状态页可能落进 BIOS 私有低内存（"下一次 INT 调用
  三重故障"类）。强制构建证明：守卫触发、内核遵循
  `oc.stmon=off`、引导完成。
- **H4 - 低 EBDA 机器的页表重定位目标落在蹦床自身地址上**，且返
  回路径硬编码 CR3。重定位目标迁移并单一事实源发布；强制构建
  矩阵：新目标可引导，旧目标在修复前后构建上都死。
- 另有：CMOS 寄存器选择保持 NMI 掩码置位；UEFI getkey 接纳 OVMF
  ConIn 可能窃取的 CSI 方向键尾字节。

### 6. 扩展排查
对最终树的三链路复审计。BIOS 菜单串口键控原本失效（SeaBIOS 下
int 14h 路径永不送达）——现改为直读 16550，实测验证。本批次自身
的一处回归（在 UEFI 下装载我们的 IDT 会杀死 OVMF 的中断驱动生态）
在发布前被捕获并修复——IDT 装载仅限 BIOS 固件。OVMF 菜单输入
饥饿登记为 K-06 并附规避方案。

## 已知问题

- **K-06 - 引导服务存活期间 OVMF 下的 OCBL 菜单无法通过键盘操
  作。** 无任何输入源送达（串口字节被 OVMF 终端驱动抽干且不再经
  ConIn 回流；PS/2 同样饥饿）——菜单在 10 秒倒计时后自动引导默认
  条目。BIOS 侧菜单键盘操作完整可用（串口 + PS/2）。候选后续修
  复：基于 WaitForEvent 的菜单等待循环。
- K-01/K-02/K-03/K-05 原样结转（见 KNOWN_ISSUES）。

证据：`evidence/wp-tui-input-encoding-hardening/`（串口原始字节
捕获与 hexdump 分析、VMware 推理链及全部测试转录、扩展排查发现、
回归门禁捕获）。
